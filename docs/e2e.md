# End to end run against the real hub

`scripts/e2e.sh` runs the compiler against the real hub inside one
container, with the hub repository's own harness (`scripts/e2e/` in the hub,
`docs/implementation/local/container-e2e.md` there): Redis, a SeaweedFS S3
gateway, the Postgres server the container provides, and the hub built from a
writable copy at `/tmp/hub`. Everything listens on loopback only. The ids in
the output (compiler, build, jobs) are random per run, generated by the hub
for its throwaway local database.

What each assertion means:

- Registry: the first `GET chunk/registry` is `202`, polling reaches `200`,
  and the body is a hub container that `describe --from-file --container`
  decodes to one section with eleven frames. The frames equal a local
  compile, and the section's bytes are identical to it.
- Cells: every non-empty cell of frame 4 at depth 1 (all eight, from
  `keys --frame 4 --depth 1`) and two empty cells. Every cell of frame 4 at
  depth 1 holds matter, so the empty cells are the first two empty ones at
  depth 2 in `(x, y, z)` order, `4-2-0-0-0` and `4-2-0-0-1`. Each reaches
  `200` with `Cache-Control: public, max-age=31536000, immutable` and
  decodes with gx-core's container decoder to one section (one layer in the
  build); the empty keys decode to one empty section.
- Mass: the summed mass of the eight depth 1 sections against frame 4's
  registry mass, limit 0.5 percent.
- Cache hit: a repeated `GET` is `200` at once with the same body, and the
  `compilation_jobs` row count for the key (`psql`) is unchanged.
- `409`: the registry bytes submitted a second time with the compiler's
  credentials. `400`: 16 zero bytes submitted as a section for a key nothing
  requested; the body is the hub's JSON rejection carrying `"code"`.

The hub logs nothing when a compiler connects (its connection registry does
not log, and ASP.NET Core request logs are at `Warning`), and it has no
endpoint listing connected compilers, so the script waits for the
compiler's own `connected to hub` log line, which follows a completed
WebSocket upgrade.

## Earlier run: depth 1 mass over the limit

The first run, before this change, failed one assertion and passed the
other 42:

```
FAIL mass over 8 non-empty depth 1 cells of frame 4: 6.006529548e+24 kg vs registry 5972168399787584000000000 kg, error 0.575355 percent (limit 0.5)
e2e: 42 passed, 1 failed
```

Depth 1 was compiled at 16 samples per axis. A body spans a quarter of each
depth 1 cell along each axis, so the ball was only 8 samples across and the
sub-sampled volume came out 0.58 percent high. This was the compiler's
fault, not the hub's: depth 1 now uses 32 samples per axis (0.086 percent,
the same as depth 2), a depth 1 conservation test was added to
`tests/compile.rs`, and the golden hash of `1-1-0-0-0` changed as recorded
in `docs/compile.md`.
